## 1. 文档维护方式

需求统一维护在本文件中，并按一期、二期划分章节。这样既能保留阶段目标和需求编号，又能在同一处同步当前实现状态，避免多份需求文档之间产生冲突。

状态定义：

- `已实现`：代码中已存在主要实现；不代表已完成生产验收。
- `部分实现`：主链路存在，但仍缺验收、完整场景或生产能力。
- `规划中`：尚未发现对应实现，或仅存在依赖/设计稿。
- `暂缓`：明确不在当前迭代范围。

本文描述的是演示/学习项目，不代表真实银行生产系统。涉及客户、账户、交易、消息发送的数据和动作均应使用脱敏 Mock 数据。

## 2. 项目目标与边界

### 2.1 目标用户

- 财富客户经理：通过自然语言查询行内规则、市场信息和 Mock 客户信息，并发起受控的消息操作。
- 系统管理员/开发者：维护技能配置、知识材料、测试集和运行配置。

### 2.2 核心目标

1. 基于内部知识材料回答问题，并返回来源。
2. 识别用户意图，将请求路由到知识问答、外部信息、客户查询、消息发送或闲聊技能。
3. 对低置信度、缺少关键参数和高风险动作提供澄清或人工确认。
4. 保存会话上下文，并确保不同会话隔离。
5. 形成可重复运行的检索、意图和端到端评估体系。

### 2.3 明确不包含

- 真实客户账户、真实核心系统或真实消息网关接入。
- 未经授权的个人信息查询、交易或营销触达。
- 将真实密钥、内网地址、客户资料或生产日志提交到 Git。
- 将当前 Mock 实现表述为已达到银行生产合规要求。

## 3. 当前系统概览

当前仓库由四个主要应用组成：

- `bank-front-end`：React + TypeScript + Vite + Ant Design 前端。
- `bank-chat-middle-platform`：Spring Boot 中台，负责会话、意图路由、技能状态、内部 Mock 技能和配置管理。
- `bank-agent-demo`：FastAPI AI 服务，负责结构化意图识别、RAG、外部信息查询和技能编排。
- `bank-streamlit`：一期 Streamlit 前端，作为历史实现保留。

部署由 Docker Compose、Redis 和 Nginx 组成。当前代码采用显式意图识别、技能路由和状态机服务；虽然 Python 依赖中包含 LangGraph，但未发现 `StateGraph` 主链路实现，因此不将“LangGraph 编排完成”列为当前成果。

## 4. 一期需求：RAG 问答 MVP

### 4.1 用户故事

#### US-01 行内规则查询

客户经理输入产品、客户分级或监管规则问题，系统返回基于知识库的回答和来源；知识库无答案时应明确兜底，不编造内容。

#### US-02 多轮追问

同一会话内支持连续提问；不同浏览器会话的历史不得互串。

#### US-03 知识库外问题拦截

对无法由内部材料支持的问题返回“未找到相关信息”或转入其他技能，不应把相近机构、相近指标误当作答案。

#### US-04 基础 Web 交互

提供聊天消息流、加载状态、清空会话和来源展示。

### 4.2 功能需求与状态

| ID | 需求 | 验收标准 | 当前状态 |
| --- | --- | --- | --- |
| R1 | 支持 PDF、Markdown、Excel 文档解析与入库 | 三类材料均能形成完整、无乱码、带来源的 chunk | 已实现，待持续回归 |
| R2 | RAG 回答附带来源 | 知识库内问题返回答案和来源标识 | 已实现 |

### 4.3 一期验收指标

- 检索：记录 Recall@3、Recall@5，不只使用最终回答准确率衡量检索。
- 边界：知识库外问题拦截率应单独统计。
- 回答：数值、单位、时间和机构名称必须与来源一致。
- 性能：目标为 10 并发下 RAG P95 小于 5 秒；需以压测报告确认，当前不得标记为已达成。

## 5. 二期需求：意图识别与多技能助手

### 5.1 用户故事

#### US-05 多技能路由

知识问答、客户资产查询、外部信息查询、消息发送和闲聊分别进入对应技能；模糊输入进入澄清流程。

#### US-06 Mock 客户信息查询

客户经理输入 Mock 客户姓名或编号，系统返回脱敏的客户摘要/AUM。没有唯一匹配时，不得猜测，应继续澄清。

#### US-07 外部信息查询

金价等时效信息进入外部信息技能，返回数据来源和时间；外部服务失败时提供可理解的降级提示。

#### US-08 消息预览与确认

系统根据 Mock 客户和模板生成消息预览。任何“发送”都必须经过确认状态；当前实现只能调用 Mock 网关，并明确标识没有真实发送。

#### US-09 意图澄清

当输入可能对应多个技能或缺少关键实体时，前端展示候选技能/补充信息，引导用户选择后继续原会话。

#### US-10 技能配置管理

管理员可以维护技能启用状态、前端可见性、快捷示例和澄清文案；配置持久化后可恢复。

## 6. 跨阶段非功能需求

### 6.1 安全与隐私

- 只使用虚构或脱敏客户数据；姓名、客户号、AUM 等 Mock 数据必须明确标注。
- 密钥只能由环境变量或本地私有配置提供，不得在文档、代码示例和日志中写入真实值。
- 内部技能接口必须鉴权；默认开发密钥不能用于共享或生产环境。
- 日志不得记录身份证号、银行卡号、手机号、真实客户姓名、完整消息正文等敏感信息。
- 高风险或外部副作用操作必须有确认、权限校验、幂等和审计能力。

### 6.2 可维护性

- 业务模板、敏感词、阈值、模型地址和技能展示配置应与代码解耦。
- Java、Python、前端之间的字段和枚举要有稳定契约，并通过契约测试防止漂移。
- 重建向量库前必须清理旧索引或使用版本化索引，避免新旧 chunk 混用。

### 6.3 可观测性与测试

- 每次请求应有 `traceId`，并记录意图、技能、耗时、结果状态和错误码。
- 单元测试覆盖意图、澄清、技能状态机和文档解析。
- 端到端测试覆盖 RAG、外部信息、客户查询、消息确认、取消和异常降级。
- 任何准确率数字必须同时记录评估集版本、样本量、判分方式和运行日期。
