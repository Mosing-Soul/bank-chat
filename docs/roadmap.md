# 项目 Roadmap

> 最后整理：2026-07-16
>
> Roadmap 只记录未来计划、迭代顺序和升级方向；已完成能力以 `requirements.md` 为准。

## 迭代原则

- 优先完成可验证的端到端闭环，再扩展新技能。
- 每个指标必须绑定固定评估集和运行记录。
- Mock 与真实系统边界保持清晰；安全能力先于真实外部副作用。
- 当前工作区存在未提交改动，里程碑状态以合并后的测试结果为准。

## R0：整理与稳定当前二期主链路

目标：将当前意图澄清、技能配置、消息状态机和 React 界面的改动收敛为可重复验证的版本。

- 完成 Python 单元测试、Java Maven 测试和前端构建。
- 联调五类意图：知识问答、客户 AUM、外部信息、消息发送、闲聊。
- 覆盖“自动路由、强制技能、低置信度澄清、确认、取消、修改、操作过期”场景。
- 校验 Java/Python/TypeScript 的请求响应字段，修复契约漂移。
- 更新 Docker Compose，正式前端与历史 Streamlit 的启用策略只能保留一个默认入口。

完成标准：从干净环境启动后，核心端到端用例全部通过并形成测试记录。

## R1：建立可信评估基线

目标：解决“系统效果问题”和“评估方法问题”混在一起的情况。

- 清洗 RAG 评估集：答案完整、来源明确、问题无歧义、计算题单独分类。
- 检索指标与生成指标分离：Recall@3/5、边界拦截率、端到端答案正确率分别统计。
- 为数值、百分比、单位和日期建立程序化比较，LLM Judge 仅处理语义型答案。
- 固化每次报告的评估集版本、代码提交、模型、参数、样本量和时间。
- 扩充意图评估集，分别统计清晰意图、缺实体、复合意图和超范围问题。

完成标准：同一版本重复运行结果稳定，误判样本可追溯到具体数据或规则。

## R2：RAG 数据与检索升级

目标：优先修复文档解析和数据建模，再讨论模型升级。

- 为普通 PDF/Markdown、产品明细表、层级表、交叉表建立明确解析策略。
- 为 Excel chunk 保留表名、机构、指标、月份、单位和父级标题。
- 引入索引版本或原子重建，禁止新旧 chunk 并存。
- 建立文档权威级别和版本元数据，处理同一术语跨文档冲突。
- 在可靠基线之上评估 BM25 + 向量混合检索和 reranker；不以“接入成功”代替效果提升。

完成标准：目标评估集的 Recall@K 有可复现提升，且边界拦截率不下降。

## R3：安全与可观测性加固

目标：让演示系统具备清晰的安全边界和排障证据。

- 移除共享配置中的开发默认密钥，启动时校验关键环境变量。
- 增加结构化审计日志、字段脱敏、日志保留周期和错误码规范。
- 为内部技能接口增加鉴权失败、重放、超时和降级测试。
- 为消息操作增加幂等键、确认人、确认时间、模板版本和完整状态审计。
- 增加服务健康检查、调用耗时和失败率指标。

完成标准：安全检查清单通过，日志可串联一次完整请求且不含敏感明文。

## R4：管理与运维能力

目标：减少通过代码或命令行维护知识和技能的成本。

- 知识库管理：文档列表、上传、删除、索引状态和版本回滚。
- 技能管理：启停、展示顺序、示例、澄清文案和阈值配置。
- 配置变更审计和回滚。
- 标准化健康检查、备份恢复、部署升级与故障处理文档。

完成标准：管理员通过界面完成一次文档更新和技能配置变更，无需直接修改数据库或代码。

## R5：三期升级方向

以下方向需在 R0-R4 稳定后择一推进：

1. LangGraph checkpoint + interrupt：将高风险操作的待确认状态持久化，支持跨进程恢复。
2. 跨技能上下文：完成“查客户 → 给他发消息”中的实体继承、冲突消解和显式确认。
3. 模型私有化：使用 vLLM 部署量化模型，并记录延迟、吞吐、显存和效果对比。
4. 意图分类方案对比：Prompt/规则/结构化输出与小模型微调的准确率、延迟和维护成本对比。
5. MCP 工具封装：仅在接口权限、确认和审计模型成熟后封装客户查询等无副作用或受控技能。

## 暂不推进

- 真实核心银行、CRM、客户数据或消息网关接入。
- 在没有权限、审计、幂等和人工确认前执行真实外部操作。
- 为追求技术栈完整而同时引入多个尚无评估依据的框架或模型。
